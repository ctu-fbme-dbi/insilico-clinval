# Reproducing the article

Which suite, pipeline config and command produced each result of the article. Try the
[quickstart](../README.md#quickstart-about-10-minutes-no-downloads) first: it runs the same
commands on a tiny genome in a minute.

The article's runs are large: five 30x whole-genome or multi-chromosome suites with two samples
each, plus the revision and side-experiment suites. Plan on a Linux server with Docker, 8+ cores,
32+ GB RAM and about 1 TB of disk. Disk, time and monitoring of the simulations are described in
[acmg_sf32_server.md](acmg_sf32_server.md).

## 1. What was run

### Test suites (`configs/suites/`)

| Suite | Content | Used in |
|---|---|---|
| `acmg_sf32_short1`, `_short2`, `_short3` | ClinGen eRepo variants in ACMG SF v3.2 genes, chr17+chr19 / chr12–chr15 / chr1+chr10+chrX, HG002 v4.2.1 background, 30x | main results, Table 1 |
| `acmg_sf32_full1`, `_full2` | the same on the whole genome (seeded random draw / one P/LP per SF gene) | main results, fidelity (full1) |
| `acmg_sf32_short1_bg10` | short1 with a 10 bp instead of a 500 bp background window | Supplementary Note S1 |
| `difficult_v5q` | variants in GIAB difficult strata, GRCh38 false duplications and paralogues; HG002 v5.0q background, simulated from the GIAB-masked GRCh38 | difficult contexts |
| `exp_indels_v5q` | ClinVar indels in six length bins, 1–100 bp | Supplementary Note S2 |
| `exp_synthetic_v5q`, `exp_synthetic_del_v5q` | synthetic novel loss-of-function variants (generated by `scripts/generate_synthetic.py` from `configs/synthetic/`) | Supplementary Note S3 |

**`acmg_sf32_full1`:** the article's run was built from `acmg_sf32_full1.prev.yaml` (see
[acmg_sf32_server.md](acmg_sf32_server.md#the-test-sets)). Use the `.prev` file for every command
on that run directory; do not edit it.

### Pipeline configs (`configs/adapters/`)

All use nf-core/sarek 3.10.0 (bwa-mem2, DeepVariant, BQSR skipped, iGenomes `GATK.GRCh38`) and
BIAS-2015 v3.0.0 (data bundle 2026.03.01):

| Config | Tertiary analysis |
|---|---|
| `sarek-3.10.0-deepvariant_bias2015-v3.0.0-nirvana` | BIAS-2015 + Nirvana 3.18.1 (baseline) |
| `..._nirvana_noPP5BP6` | the same with PP5/BP6 (database evidence) switched off |
| `..._vep`, `..._vep_noPP5BP6` | BIAS-2015 + Ensembl VEP 115, with and without PP5/BP6 |
| `sarek-3.10.0-deepvariant-haploidXY_bias2015-v3.0.0-nirvana` | controlled change: DeepVariant calls chrX/chrY as haploid in XY samples (regression diff) |

Acceptance criteria: `configs/acceptance/article-default.yaml` (an example configuration, not a
clinical standard).

## 2. Data

```bash
python scripts/fetch_data.py --list                                   # everything available
python scripts/fetch_data.py --only grch38,giab_hg002_v4.2.1          # curated suites
python scripts/fetch_data.py --only giab_hg002_v5.0q,grch38_giab_v3_masked,giab_strata_v3.6  # revision suites
python scripts/fetch_data.py --only bias2015_erepo_benchmark_v2.2.0   # held-out reference
python scripts/fetch_data.py --only bias2015_hg38,nirvana_grch38,nirvana_grch38_updates      # BIAS-2015 + Nirvana
python scripts/fetch_data.py --only bias2015_hg38_vep,vep_hg38_annotations,vep_cache_grch38_115,gnomad_v4.1_exomes  # BIAS-2015 + VEP (~330 GB)
python scripts/fetch_data.py --only giab_strata_v3.3,giab_cmrg_v1.00,hg002_novaseq_30x       # fidelity (44 GB FASTQ)
python scripts/fetch_data.py --only clinvar_20260928                  # exp_indels_v5q
```

Pinned data sets are verified by SHA-256; unpinned ones (moving exports) are hashed into
`data/fetch_report.json` and every run manifest. Some fetches need a tool image first (Nirvana,
VEP); `--list` says which.

**ClinGen eRepo export.** eRepo changes daily and has no versioned download. The curated suites
were selected from the export of 2026-10-15 (`data/clingen/erepo_2026-10-15.tsv`, SHA-256
`a7aba27b6308da9f3c8b64374c236abc6681f1bcb25d448fb22009e324899795`), which is archived with the
article's data. A fresh download selects different variants; the suites then still run, but
`variants.selected.tsv` differs from the article's.

ClinGen releases its curated content under CC0 1.0
([ClinGen Terms of Use](https://clinicalgenome.org/docs/terms-of-use/)); the archived snapshot
carries the same dedication, not the licence of this repository. ClinGen asks for attribution with
the date accessed: cite Rehm et al., *N Engl J Med* 2015 (doi:10.1056/NEJMsr1406261) and the
ClinGen curation paper in *Genet Med* 2024 (doi:10.1016/j.gim.2024.101228). The classifications
are not intended for direct diagnostic use.

## 4. Steps per suite

`S` is a suite name, `P` a pipeline config name, `RT` the runtime config.

```bash
RT=configs/runtime/docker-local-build.yaml
SUITE=configs/suites/$S.yaml          # acmg_sf32_full1: configs/suites/acmg_sf32_full1.prev.yaml

# 1-3: truth and reads (whole genomes: one sample at a time, see acmg_sf32_server.md)
clinval validate-suite $SUITE
clinval build-truth --suite $SUITE
clinval simulate    --suite $SUITE --runtime $RT

# held-out status of the eRepo variants (BIAS-2015 was tuned on eRepo v2.2.0)
clinval held-out --suite $SUITE \
    --reference data/clingen/bias2015_erepo_v2.2.0_benchmark.grch38.vcf --release v2.2.0 \
    --approved-after 2025-02-02

# 4-5: the system under test
clinval run-sut --suite $SUITE --pipeline configs/adapters/$P.yaml --runtime $RT
# 6: comparison
clinval compare --suite $SUITE --pipeline configs/adapters/$P.yaml --runtime $RT \
    --pipeline-reference <FASTA Sarek aligned to>
```

Without `--out`, every command writes to `runs/$S` (`output.directory` of the suite).

**Sarek once, four tertiary configs.** All four article configs share the same secondary
analysis. Run Sarek once (the first `run-sut`, or `nextflow run nf-core/sarek` by hand with the
same parameters), then let the other configs adopt its results instead of rerunning it:

```bash
clinval run-sut --suite $SUITE --pipeline configs/adapters/$P.yaml --runtime $RT \
    --sarek-results <sarek outdir>
```

`--sarek-results` checks that the Sarek run used the release, parameters and FASTQ files of the
pipeline config, and records the adopted run in the manifest.

## 5. Results

### Metrics and acceptance (main results)

```bash
for P in sarek-3.10.0-deepvariant_bias2015-v3.0.0-{nirvana,nirvana_noPP5BP6,vep,vep_noPP5BP6}; do
  clinval metrics --pipeline configs/adapters/$P.yaml \
      --run runs/acmg_sf32_short1 --run runs/acmg_sf32_short2 --run runs/acmg_sf32_short3 \
      --run runs/acmg_sf32_full1 --run runs/acmg_sf32_full2 \
      --out results/$P --acceptance configs/acceptance/article-default.yaml \
      --par-bed configs/regions/grch38_par.bed
done
```

Per-variant outcomes and failure stages (failure-stage figure): `runs/<suite>/sut/<P>/compare/outcomes.tsv`.

### Regression diff (controlled change)

The baseline and the haploid-chrX candidate, both run (`run-sut`, `compare`) on
`acmg_sf32_short3`. The candidate realigns all reads, so its autosomal calls also repeat the
baseline: the diff's "Secondary concordance" table is the run-to-run noise.

```bash
clinval diff \
    --baseline  configs/adapters/sarek-3.10.0-deepvariant_bias2015-v3.0.0-nirvana.yaml \
    --candidate configs/adapters/sarek-3.10.0-deepvariant-haploidXY_bias2015-v3.0.0-nirvana.yaml \
    --run runs/acmg_sf32_short3 --out results/diff_haploidXY --par-bed configs/regions/grch38_par.bed
clinval report --metrics results/sarek-3.10.0-deepvariant_bias2015-v3.0.0-nirvana \
    --diff results/diff_haploidXY --out results/report.md
```

Changes of the tertiary analysis are diffed the same way on all five suites, e.g. `--baseline
..._nirvana.yaml --candidate ..._nirvana_noPP5BP6.yaml` with one `--run` per suite.

### Fidelity of the simulated reads (Results 3.1)

The positive sample of `acmg_sf32_full1` and the real HG002 genome (`hg002_novaseq_30x`) go
through the same Sarek configuration; only the input FASTQ differs. For the real genome, write
the Sarek samplesheet by hand (`patient,sex,status,sample,lane,fastq_1,fastq_2`, one row per lane)
and run Sarek with the same `params.yaml`. Set the Sarek output paths in
`configs/fidelity/hg002_full1.yaml`, then:

```bash
clinval fidelity --config configs/fidelity/hg002_full1.yaml --out runs/fidelity_hg002 \
                 --step planting                         # needs all five suites simulated
clinval fidelity --config configs/fidelity/hg002_full1.yaml --out runs/fidelity_hg002 \
                 --runtime configs/runtime/docker.yaml --step qc --step calling
```

Outputs: `fidelity.json`, `fidelity_calling.tsv`, `fidelity_qc.tsv`, `planting.tsv`. Each step
keeps its raw tool output, so a failed step can be repeated alone. DeepVariant's released models
were trained on GIAB samples, which makes absolute recall optimistic for both the simulated and the
real genome alike.

### Background versions (Discussion)

Differences between the HG002 v4.2.1 and v5.0q backgrounds around the planted variants, without
running any pipeline:

```bash
python scripts/background_diff.py --old configs/suites/acmg_sf32_full1.yaml \
    --new configs/suites/difficult_v5q.yaml \
    --run runs/acmg_sf32_short1 --run runs/acmg_sf32_short2 --run runs/acmg_sf32_short3 \
    --run runs/acmg_sf32_full1 --run runs/acmg_sf32_full2 --out results/background_diff
```

### Supplementary experiments

- **Background window (Note S1):** run `acmg_sf32_short1_bg10` like `acmg_sf32_short1` and compare
  the two `outcomes.tsv` variant by variant.
- **Indel length (Note S2):** `exp_indels_v5q`; calling by length bin is in
  `sut/<P>/compare/<sample>.calling.json`.
- **Synthetic novel variants (Note S3):** the committed suites `exp_synthetic_v5q` and
  `exp_synthetic_del_v5q` are ready to run. To regenerate them (needs `mane_v1.5`,
  `clingen_gene_curation`, gnomAD and VEP), see the docstring of `scripts/generate_synthetic.py`;
  the generator's reports are in `configs/synthetic/*_reports/`.

### Runtime and cost

Run time and peak memory of every step are in each `run_manifest.json` (`steps`). The article's
cost estimates were measured on Amazon Web Services with separate scripts that are not part of
this repository.
